# Gold to OSDU, column by column

Generated by `scripts/osdu_report.py` from `src/hugin/osdu/mapping.py` on
2026-08-13. Do not edit this file; edit the mapping and regenerate. The point of
generating it is that the document and the code cannot drift apart, which is
what happens to every schema mapping maintained as prose.

SPEC.md section 7 cuts a real OSDU deployment: mapping plus validator is the
deliverable. ADR 008 argues that line. What follows is therefore a *mapping*
that runs and is schema-checked, not an integration.

## The three kinds

| Gold table | OSDU kind | Grain change |
|---|---|---|
| `gold.dim_wellbore` | `osdu:wks:master-data--Wellbore:1.0.0` | none - a version is a version |
| `gold.fct_log_sample` | `osdu:wks:work-product-component--WellLog:1.0.0` | **aggregates** - one per run |
| `gold.fct_trajectory` | `osdu:wks:work-product-component--WellboreTrajectory:1.0.0` | **aggregates** - one per survey |

The two aggregations are the substance of this mapping. OSDU's
work-product-components describe a logging run and a survey; the readings and
the stations live in bulk datasets those records point at. A mapping that
emitted one OSDU record per fact row would be a mapping written without reading
the schema.

## Gold columns with no OSDU home

The interesting half. A column here is not omitted by oversight; it has
nowhere to go, and the reason is the point.

| Column | What it is | Why it does not map |
|---|---|---|
| `dim_wellbore.wellbore_key` | surrogate key | An OSDU id is the identifier. Exporting an md5 that means something only inside this warehouse would create a second identity for the same wellbore, which is the exact failure BR-12 exists to prevent. |
| `dim_wellbore.is_current` | SCD2 flag | Implied by OSDU record versioning. See version_number above. |
| `fct_log_sample.value / depth_m` | the measurements | Bulk data. Belongs in a dataset record, not in the WPC. |
| `fct_log_sample.row_hash` | dedup key | Internal to the lakehouse; means nothing outside it. |
| `fct_trajectory.station_*` | the survey stations | Bulk data, for the same reason as the log readings: OSDU keeps the stations in a dataset the record points at, not in the record. What does survive is their envelope - top and base measured depth, and which properties the survey carries. |
| `fct_trajectory.dogleg_severity_deg_per_m` | computed by BR-09 | Derived per station and therefore bulk. OSDU would recompute it. |
| `fct_production_daily.*` | the whole production fact | Out of scope for these three kinds. Production maps to work-product-component--ProductionData in newer OSDU releases; SPEC.md section 6 names three kinds and this maps three. |
| `fct_drilling_state.*` | rig states, BR-06 | No OSDU well-known schema covers a derived rig-state classification. It would be an extension on a Wellbore Activity record, which is not one of the three kinds mapped. |

## OSDU properties this mapping leaves empty

Read this list before believing any claim about OSDU readiness. Each
of these is a property the schema defines, that a real platform would
want, and that nothing in this repository can honestly fill.

| OSDU property | What it would take |
|---|---|
| `acl.owners / acl.viewers` | Real group identifiers from the entitlements service. |
| `legal.legaltags` | A legal tag created in the target partition. The Volve CC BY 4.0 terms would be its basis. |
| `data.SpatialLocation` | A surface location with a CRS. Not in gold; the trajectory carries offsets, not coordinates. |
| `data.VerticalMeasurements` | A datum elevation. Not in any source read so far. |
| `data.TrajectoryTypeID` | A reference-data value. The sources do not say gyro or MWD. |
| `data.PrimaryMaterialID` | Reference data about the produced fluid. Inferable from well_role, and deliberately not inferred. |
| `data.Datasets` | Bulk dataset records for the log readings and the survey stations. Nothing here writes them. |
| `data.ServiceCompanyID` | An Organisation master record for Baker Hughes, Schlumberger and the rest. |
| `data.FacilityTypeID` | A reference-data value for 'wellbore'. Trivially fillable, and left empty because reference data has to come from the target partition rather than be invented here. |

## Validation

```
python -m hugin.osdu.validate_osdu --write data/osdu   # map gold, validate, write
python -m hugin.osdu.validate_osdu --records data/osdu # validate from disk, no Trino
```

The schemas in `src/hugin/osdu/schemas/` are **reduced local copies** of
the published OSDU 1.0.0 well-known schemas - that directory's README
says exactly what was kept and what was dropped. A pass means the
envelope, the kind, the id form and every mapped property are right. It
does not mean an OSDU instance would accept the record: the table above
lists what is still missing.

`tests/test_osdu.py` runs the whole mapping over fixture rows and
validates the output, so the mapping is covered in CI without a
warehouse and without a platform.
